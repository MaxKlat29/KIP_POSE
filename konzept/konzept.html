POSE

6D-Pose-Estimation für Roboter-Pick-and-Place — wie der Roboter aus einem Top-Down-Foto erkennt, welche Bauteile wo und wie liegen.
Version · 0.1 (Konzept) Datum · 2026-05-17 Setup · Roboterarm + Top-Down-Kamera + CAD-Bibliothek Compute · RTX 3090 (lokal)

Was wir bauen

Eine ML-Pipeline, die aus einem RGB-Foto von oben auf eine Tischplatte liest, welche Bauteile dort liegen (Klassifikation + Lokalisierung) und in welcher räumlichen Orientierung (6D-Pose: Position + Rotation). Die Ausgabe ist eine rekonstruierte 3D-Szene — alle Bauteile mit ihrer Pose im Tisch-Koordinatensystem (und optional ins Roboter-Koordinatensystem transformiert), visualisierbar in einem 3D-Viewer.

Warum 6D — nicht 2D?

Klassische 2D-Detektion findet zwar wo im Bild ein Teil ist, sagt aber nichts über seine Orientierung. Eine flach liegende Mutter sieht in 2D anders aus als eine hochkant stehende — der nachgelagerte Greifplaner braucht die exakte 3D-Lage, sonst greift der Roboter ins Leere oder verkantet das Teil.

Scoping — fester Bauteilkatalog

Wir arbeiten ausschließlich mit Bauteilen mit bekanntem CAD-Modell. Keine "unseen objects". Das erlaubt uns, eigene Modelle gezielt auf den Bauteilkatalog zu trainieren statt auf generalisierende Forschungsmodelle zu setzen — deutlich präziser für das feste Set.

TL;DR — Wie wir das lösen

POSE nutzt die Planar-Tatsache aggressiv aus: pro Bauteil analysieren wir per Drop-Simulation, welche Mesh-Face den Tisch berührt (z. B. Schraube → seitlich oder auf einer Spitze; Würfel → 6 Seiten; L-Bracket → 4 Varianten). Daraus ergeben sich X diskrete Liegevarianten pro Bauteil. Die Pipeline besteht aus drei Modellen, alle trainiert auf synthetischen Daten: Detection (YOLOv8) findet wo + was, Variant-Klassifikator entscheidet welche Liegevariante, Yaw-Regressor bestimmt nur noch die 2D-Drehung. 3D-Pose ist damit nicht regrediert sondern konstruiert — präziser, robuster, kein 6D-Refinement nötig.

Die Pipeline in drei Phasen

PHASE A
Vorbereitung & Training
Kamera einmessen, CAD-Bibliothek aufbauen, synthetische Trainingsbilder simulieren (30–50k Frames), stabile Liegelagen pro Bauteil vorberechnen, Detection- und Pose-Modelle auf den eigenen Synth-Daten trainieren.
PHASE B
Inferenz (pro Foto)
Bauteile detektieren (BBox+Klasse) → Liegevariante klassifizieren (welche Face liegt unten?) → Yaw-Rotation regredieren → 3D-Szene im Tisch-KS konstruieren → in 3D-Viewer anzeigen.
PHASE C
Eval
BOP-Standard-Metriken (AR, ADD), Worst-Examples-Viewer, Sim-vs-Real-Vergleich. Acceptance: AR ≥ 0.70 auf eigenem Test-Set.

1. Setup & Anforderungen

Was wir mitbringen

  • Roboterarm über einer ebenen Tischplatte.
  • Top-Down-Kamera (RGB), in fester Position über dem Tisch.
  • CAD-Bibliothek aller Bauteile (STL/STEP), die der Roboter greifen können soll.
  • Bestehende Physics-Sim (Blender + Python), die wir auf BlenderProc-Standard umstellen.
  • GPU-Workstation: RTX 3090 (24 GB), CUDA-Stack, lokale Inferenz.

Was die Pipeline liefert

  • Pro Foto eine JSON-Liste erkannter Bauteile.
  • Pro Bauteil: object_id, pose_4x4 (Welt-Koordinaten), confidence, stable_lage_idx.
  • Inferenz < 1 s pro Frame, AR ≥ 0.70 auf Test-Set.
  • Erweiterbar: neue Bauteile via CAD-Modell + neuer Trainings-Run (~30–90 min pro Bauteil-Pose-Modell + YOLO-Re-Training auf erweitertem Set).

2. Gesamtarchitektur

Die Architektur trennt klar zwischen einmaliger Vorbereitung (Phase A, links) und wiederkehrender Inferenz (Phase B, rechts). Phase A produziert Artefakte (Modelle, Templates, Liegelagen-Tabellen, Kalibrierung), die Phase B verwendet.

Abb. 1 — Gesamtarchitektur. Links: Vorbereitung. Rechts: sieben sequenzielle Inferenz-Stufen. Violette gestrichelte Pfeile zeigen, wie die vortrainierten Modelle in die Inferenz-Stufen einfließen.

Drei Säulen, die das Konzept tragen

  1. Synth-Daten statt Real-Labels — 30–50k synthetische Top-Down-Bilder mit perfekter Ground-Truth aus den CAD-Modellen. Manuelles Labeln entfällt.
  2. Pose nicht regredieren, sondern konstruieren — pro Bauteil bestimmen wir per Drop-Simulation, welche Mesh-Faces als Bottom-Face vorkommen können. Die Pipeline klassifiziert dann nur noch welche Variante vorliegt + den Yaw-Winkel — die 3D-Pose folgt deterministisch.
  3. Drei einfache Modelle statt ein komplexes — Detection (YOLOv8) + Variant-Klassifikator + Yaw-Regressor. Jedes Modell hat eine klar definierte, kleine Aufgabe, alle trainieren wir selbst auf unseren Synth-Daten.

3. Phase A — Vorbereitung (einmalig pro Bauteil-Set)

3.1 Synth-Datengenerierung BlenderProc + PyBullet

BlenderProc (Open-Source, DLR) ist der De-facto-Standard für BOP-konforme synthetische Trainingsdaten. Aus den CAD-Modellen werden zigtausend Top-Down-Frames gerendert — jedes mit randomisierten Materialien, Lichtern und HDRI-Hintergründen. Die Position der Bauteile entsteht durch eine PyBullet-Physik-Simulation: virtuelle Teile fallen auf den simulierten Tisch und kommen in stabilen Lagen zur Ruhe.

InputCAD-Bibliothek (STL/OBJ), Tisch-Geometrie, Kamera-Modell
Wie5–15 zufällig gewählte Teile pro Frame → PyBullet-Drop → Pose-Settle → PBR-Rendering aus Top-Down-View → Domain-Randomization (Materialien, Lichter, HDRI, leichter Kamera-Jitter)
OutputBOP-Format: train_pbr/<scene>/<frame>.png + scene_gt.json (perfekte Pose pro Teil) + Masken + Depth optional
Volumen30–50k Frames pro Run (BOP-Standard), ~8–12 h auf RTX 3090

3.2 Liegevariant-Analyse Drop-Sim + Bottom-Face-Cluster

Pro Bauteil N=200 Drops in PyBullet. Für jeden Drop bestimmen wir, welche Mesh-Face den Tisch berührt (Bottom-Face). Cluster nach Bottom-Face = kleine Liste an Liegevarianten pro Bauteil. Die Drehung um die Hochachse (Yaw) wird hier ausgeklammert — sie ist innerhalb einer Variante kontinuierlich variabel und wird in der Inferenz separat geschätzt. Beispiele: Schraube = 3 Varianten (seitlich rotationssymmetrisch, auf Kopf, auf Spitze); Würfel = 6 (eine pro Seite); asymmetrisches L-Bracket mit Bohrung = 4. Drop-Häufigkeiten gewichten die Trainings-Sampling-Verteilung.

Abb. 2 — Liegevarianten als Funktion der Bottom-Face: Schraube hat 3 (seitlich, auf Kopf, auf Gewinde-Spitze). Yaw-Rotation (um Hochachse) wird nicht in der Variante kodiert, sondern separat regrediert.

3.3 Trainings-Renderings pro Variante ~Variant × Yaw-Sampling

Pro Bauteil und pro Liegevariante rendern wir das CAD-Modell für 36 Yaw-Winkel (10°-Schritte) — bei einer Schraube also 3 Varianten × 36 = ~100 Templates, bei einem Würfel 6 × 36 = 216. Diese Renderings bilden die Trainings-Targets für den Variant-Klassifikator (Label = Variant-ID) und den Yaw-Regressor (Label = Yaw-Winkel). Ergebnis pro CAD: <cad-id>/variants/<v_id>/<yaw>.png + Labels. Render-Zeit pro Bauteil: ca. 5 Minuten.

3.4 Kamera-Kalibrierung & Modell-Training

Kalibrierung (OpenCV, einmalig): Schachbrett-Aufnahmen → Brennweite/Bildmitte/Verzerrung; Tisch-Markierungen → Ebenengleichung via RANSAC. Re-Kalibrierung bei Kamera-Bewegung.

Modell-Training (~6–10 h gesamt): YOLOv8 Detection auf 30–50k Synth-Frames, alle Bauteile als Klassen, ~6–8 h. Variant-Klassifikator (CNN): 128×128-Crop → Variant-Wahrscheinlichkeit, ~30 min. Yaw-Regressor (kleiner CNN): Crop + Variant → sin/cos-Yaw, ~30 min.

4. Phase B — Inferenz (pro Foto)

Fünf sequenzielle Stufen, end-to-end < 200 ms pro Frame auf RTX 3090. Statt ein einzelnes komplexes 6D-Pose-Modell zu trainieren, lösen wir das Problem über drei spezialisierte einfache Modelle (Detection, Variant-Klassifikation, Yaw-Regression) plus deterministische 3D-Konstruktion am Schluss.

SchrittWas passiertWerkzeugLatenz
1 · Foto RGB-Frame von der Top-Down-Kamera, 1920×1080. Kamera-SDK ~5 ms
2 · Detektion YOLOv8 (trained auf 30–50k Synth-Frames) findet alle Bauteile im Bild. Output: BBox + Klasse (object_id) + Konfidenz pro Teil. Bestimmt wo + was, nichts über Orientierung. YOLOv8 (custom) ~30–50 ms
3 · Variant-Klassifikation Pro Detection Crop (128×128) extrahieren. Klassifikator gibt die Liegevariante aus (welche Mesh-Face liegt unten?). Bei einer Schraube also 1 aus {seitlich, auf Kopf, auf Spitze}. Damit ist Roll + Pitch eindeutig. CNN (custom) ~10 ms/Crop
4 · Yaw-Regression Pro Crop + Variant: kleines CNN regrediert nur den Drehwinkel um die Hochachse (sin/cos-Encoding für Periodizität). Bei rotationssymmetrischen Varianten wird der Yaw als nicht definiert markiert. CNN (custom, leicht) ~5 ms/Crop
5 · 3D-Konstruktion + Viewer Variant + Yaw → CAD wird in die bekannte stabile Pose (aus Phase A 3.2) gelegt, um Yaw rotiert, dann an die Welt-Position (aus BBox-Center via Kamera-Intrinsics + Tisch-Ebene) verschoben. Output: 3D-Szene mit Pose im Tisch-Koordinatensystem, optional ins Roboter-KS transformiert. Visualisierung in Three.js-Viewer. numpy + Three.js ~15 ms

Deep-Dive 1 — Warum nicht direkt 6D-Pose regredieren?

Die "klassische" Lösung wäre ein einzelnes Netz, das aus dem Crop direkt eine 6D-Pose ausgibt (3D-Position + 3 Rotations-Achsen). Das ist aber schwer zu trainieren: das Modell muss lernen, dass eine Pose-Differenz von z. B. 180° um die Schraubenachse kein Fehler ist (Rotations-Symmetrie), während eine Differenz von 90° zwischen "liegt seitlich" und "steht auf Kopf" ein riesiger Sprung im 3D-Raum ist. Klassische Pose-Loss-Funktionen ignorieren das.

Unser Ansatz baut diese Struktur als Induktiv-Bias ein: die diskreten stabilen Lagen sind durch die Physics-Sim bekannt; die Pipeline muss nur klassifizieren welche. Yaw wird separat regrediert weil dort die kontinuierliche Variation natürlich ist. Effektiv: schweres Problem (6D-Pose-Regression) durch einfaches Problem (Klassifikation + 1D-Regression) ersetzt.

Deep-Dive 2 — Wie konstruieren wir die 3D-Pose? (Schritt 5)

Sobald Variant und Yaw bekannt sind, ist die 3D-Pose deterministisch — keine ML-Approximation mehr:

  1. Stabile-Pose-Lookup: Variant-ID → die in Phase A 3.2 vorberechnete stabile 3D-Pose-Matrix des CAD im Tisch-Koordinatensystem (z. B. "Schraube seitlich" = Schaft-Achse parallel zur Tischebene, Z=Schaft-Durchmesser/2).
  2. Yaw anwenden: Rotation um die Hochachse, Winkel aus dem Yaw-Regressor.
  3. Position aus BBox-Center: Pixel-Mitte der Detection → via Kamera-Intrinsics + Tisch-Ebene auf 3D-Welt-Position projizieren (siehe Mapping-Mathe nächste Seite).

Das Resultat ist genau so präzise wie unsere Bottom-Face-Cluster + Yaw-Regressor. Es gibt nichts mehr zu "snappen", weil die Pose nie das Korsett der stabilen Lagen verlässt — sie wird direkt darin konstruiert. Anschaulich: das Top-Down-Bild ist die orthografische Projektion des CAD-Modells in dieser stabilen Pose mit dem geschätzten Yaw. Wir legen das CAD im Viewer einfach exakt so hin.

5. Detail: 2D → 3D Mapping

Aus einem Bild-Pixel allein lässt sich keine 3D-Position bestimmen — der Pixel entspricht einem Strahl von der Kamera durch die Welt. Wir brauchen eine Zusatzannahme. Bei uns: das Bauteil liegt auf einer bekannten Ebene (Tischplatte).

Wir tun das in drei Schritten:

  1. Strahl rückprojizieren: Aus Pixel (u, v) und Kamera-Intrinsics K wird der 3D-Strahl r = K⁻¹ · (u, v, 1) im Kamera-Frame berechnet.
  2. Strahl mit Tisch-Ebene schneiden: Tisch-Ebene ist als Normale n und Abstand d im Kamera-Frame bekannt. Schnittpunkt: t = d / (n · r); die Welt-Position ist t · r.
  3. Rotation transformieren: Die im Kamera-Frame geschätzte Rotation wird via Cam→World-Extrinsics in Welt-Koordinaten gedreht.

Die Pose-Estimator liefern die Pose im Kamera-Frame; wir transformieren sie ins Tisch-Koordinatensystem (Primärausgabe) und optional weiter ins Roboter-Basis-Koordinatensystem. Die Cam→Tisch- und Tisch→Roboter-Transformationen sind beide einmalige Setup-Größen.

Warum Tisch-KS als Primär? Weil der Tisch unsere physische Referenz ist: Bauteile liegen darauf, die Tischebene ist via Kalibrierung bekannt, und das KS ist intuitiv (X/Y in der Ebene, Z senkrecht hoch). Die Roboter-Transformation ist eine reine Multiplikation mit einer konstanten Matrix.
Abb. 3 — Pixel → Welt-Mapping. Aus Pixel (u, v) wird über die Kamera-Intrinsics K der Strahl r berechnet. Der Schnittpunkt des Strahls mit der Tisch-Ebene ist die Welt-Position des Bauteils.
